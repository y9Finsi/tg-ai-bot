# memory/gotchas.md — Грабли, лимиты и подводные камни

## 1. Telegram API & Экранирование
- **MarkdownV2 парсинг:** Telegram выбрасывает ошибку `Bad Request: can't parse entities`, если в тексте ответа есть неэкранированные спецсимволы MarkdownV2 (`.`, `!`, `-`, `(`, `)`, `_`, `*` и др.). В `src/` используется специальный хелпер очистки/экранирования. Всегда используй хелперы отправки сообщений вместо сырого `ctx.replyWithMarkdownV2` с непроверенным LLM-текстом.
- **Telegram Rate Limits:** При рассылках (`broadcast`) и постинге в каналы лимит составляет не более 30 сообщений в секунду для разных чатов и не более 1 сообщения в секунду в один и тот же чат/канал. Для этого используется очередь `BullMQ` с `limiter`.

---

## 2. ESM и Импорты в Node.js
- Проект использует чистый ESM (`"type": "module"` в `package.json`).
- **Все локальные относительные импорты ОБЯЗАНЫ содержать расширение `.js`** (например, `import { pool } from './database.js';`). Без `.js` Node.js упадет с ошибкой `ERR_MODULE_NOT_FOUND`.
- `__dirname` и `__filename` не определены по умолчанию в ESM. Используй `fileURLToPath(import.meta.url)` и `path.dirname()`.

---

## 3. Микросервис Semantica & Фолбэки
- Микросервис `semantica-service` работает по HTTP на порту 8081.
- Имеет жесткие таймауты: `SEMANTICA_TIMEOUT_MS` (по умолчанию 180ms) для выборки контекста, чтобы не задерживать ответ пользователю.
- Если сервис недоступен или ответил ошибкой, пайплайн обязан выполнить **graceful fallback** (использовать недавнюю историю из PostgreSQL без семантических векторов), а не прерывать генерацию ответа.

---

## 4. База данных и соединения
- При выполнении транзакций через `const client = await pool.connect()` обязательно помещай работу в блок `try ... finally { client.release(); }`. Забытый `release()` быстро исчерпает пул соединений PostgreSQL (`max: 20`) и повесит все запросы.
- Числовые типы PostgreSQL (`BIGINT`) приходят в JS как `string` или `BigInt`. Обращай внимание при сравнении `telegram_id`.

---

## 5. Radiant Engine Concurrency
- Суточный цикл Radiant (`day_runner.js`) обновляет состояние потребностей и текущего действия персонажа в фоне.
- При формировании контекста ответа (`context_builder.js`) данные Radiant считываются атомарно из кэша/репозитория, чтобы состояние не мутировало посреди сборки промпта.

---

## 6. Запуск тестов
- Тесты написаны под встроенный `node:test` раннер: `npm test` (`node --test --test-force-exit test/*.test.js`).
- Флаг `--test-force-exit` необходим, так как открытые пулы Redis и Postgres могут удерживать event loop активным после завершения ассертов.

## 7. Генерация картинок и дедупликация в канале
- **Запрет текста на AI-картинках:** Диффузионные модели (Gemini, Imagen, Flux) рендерят текст, если в промпте передавать текст поста. В `src/services/image_generator.js` и `src/channel_poster.js` используется строгое правило `STRICTLY NO text, words, letters, captions` и передается только описание сцены/вайба.
- **Строгий запрет повторов в канале:** В `getRandomLeraPhoto({ excludeChannelUsed: true })` и `getRandomChannelContent({ excludeRecent: true })` отключен LRU-повтор: если все фото/мемы уже были в канале, возвращается `null`, чтобы не спамить дубликатами. При генерации AI-фото его ID (`photo:${id}`) сразу связывается с `provenance.media_content_id`.

## 8. Мультимодальный пайплайн и голосовые сообщения
- **Изоляция Follow-up для `send_voice`:** При вызове тула `send_voice` нельзя скармливать синтезированный текст обратно в LLM с инструкцией «ответь своими словами». Модель может счесть это дублированием и выдать мета-рассуждения («НЕ повторяй текст...»).
- **Дебаунс и `typing_manager`:** В `flushUserBuffer` для вызова `startTyping` обязательно используется `buf.batchId || String(userId)`, чтобы `stopTyping` в очереди `queue.js` корректно очищал интервал отправки `sendChatAction`.
- **Строгий запрет повтора фото в личном чате:** В `findLocalPhoto` (`send_photo.js`) удален сброс фильтра `sentPhotoIds`. Если все локальные фото из базы просмотрены, бот не крутит их повторно, а генерирует новое фото через нейросеть либо честно отказывает.

## 9. Telegram Guest Mode (Bot API 8.0+) & Платежные методы
- **Guest Mode (`guest_query`):** При вызовах `@gexyy_bot <запрос>` в чатах, где бот не состоит в участниках, Telegram присылает обновление `guest_query`. Отвечать в такие чаты можно ТОЛЬКО через `bot.telegram.callApi('answerGuestQuery', { guest_query_id, result: { type: 'article', id, title, input_message_content: { message_text } } })`. Обычный `sendMessage` в чужой чат выбросит 403 Forbidden.
- **Коллизия REACTION режима в Guest Mode:** Telegram Bot API не поддерживает эмодзи-реакции на гостевые запросы. Для любого публичного/гостевого контекста (`isPublicContext: true`) флаг `allowReaction` принудительно отключается (`allowReaction = false`), чтобы классификатор интентов не сбрасывал текстовый ответ в пустую строку (`text: ''`), а всегда вызывал LLM для генерации ответа.
- **Нормализация параметров зачисления балансов (`processPlategaPayment`, `grantPackage`):** Всегда поддерживать гибкие сигнатуры аргументов (как строковый `packageType`, так и раздельные числовые `textCount`/`imgCount`), чтобы не терять начисления при вызовах из разных частей бота, админки и вебхуков.

## 10. Автопостинг в канал и Режиссёр (Jev Story Engine)
- **Утечка JSON Story Director в канал:** При использовании эталонного промпта Story Director с требованием JSON-вывода (`text`, `photoprompt`, `steps`), функция `cleanResponseText` в `src/utils/response_text.js` автоматически распаковывает JSON-структуру, чтобы сырой JSON не публиковался в Telegram-канал.
- **Единый конвейер публикаций:** `generateAndPublishChannelPost` в `src/channel_poster.js` теперь в первую очередь использует Режиссёра (`createPendingStory` + `publishStoryToChannel`), передавая актуальные темы из `topic_harvester`, живую лесенку сообщений, нативные медиа и комментирование первоисточников. Фоллбек на старый драфт срабатывает только при полном отсутствии доступных тем.

---

## 11. Мультидиалог в группах и генерация медиа
- **Свежая генерация фото (`send_photo`):** В группах и гостевом режиме принудительно отключается `allow_db_fallback` (`allowFallback = false`). Фото всегда генерируются на лету через нейросеть, предотвращая ситуации, когда один участник видит повторы готовых картинок из галереи базы данных, которые уже видел другой.
- **Одиночный перенос строк вместо `|||`:** В гостевом режиме и группах разделитель лесенки `|||` заменяется на одиночный перенос строки `\n` без двойных пустых строк, сохраняя компактность и естественность реплик.

---

## 11. Reasoning-модели (DeepSeek/Qwen) и Tool Calling
- **Обязательный массив `required` в JSON Schema тулов:** Reasoning-модели перед вызовом инструментов строят логическую цепочку внутри `<think>`. Если поля схемы опциональны, модель может решить не вызывать инструмент, а спросить пользователя об одежде в мыслях и закрыть `</think>` с пустым `content`. Обязательно указывать `required: ["prompt", "outfit", "time_of_day"]` в `send_photo.js` и запрещать переспрашивать лук в описании параметров.
- **Graceful Silence вместо шаблонных заглушек:** В публичном контексте (`isPublicContext: true`) при сбое валидатора или пустом ответе после ретрая движок возвращает пустой текст `""`. В `channel_comments.js` при пустом тексте сообщение в чат не отправляется (бот просто молчит), сохраняя реализм живого человека и исключая шаблонные фразы («ой я тут зависла»).

## 12. Словесные обещания LLM vs Реальный вызов `schedule_followup`
- **Проблема словесного ролеплея:** Модели склонны давать бытовые обещания на словах («давай вечером скину трек», «пойду в душ, через часик напишу», «ща доеду черкану») чистым текстом, пропуская вызов инструмента `schedule_followup`. В результате в очереди BullMQ задачи нет, и бот никогда не возвращается.
- **Решения:**
  1. **Deterministic Output Interceptor (Эвристический перехватчик ответа):** Если в исходящем тексте модели обнаружены обещания будущего действия («давай вечером скину», «напишу через час», «скину позже»), а `toolsExecuted` не содержит `schedule_followup` — движок автоматически ставит `enqueueFollowupPromise` на основе распарсенного времени (или к вечеру в 20:00–21:00 MSK).
  2. **Strict Judge Rule (Браковка судьей):** Правило для судьи `UNFULFILLED_PROMISE`: браковать ответ, если модель обещает вернуться/скинуть что-то позже, но не вызвала инструмент, с принудительным ретраем.
  3. **Снятие отложенных задач (`cancelFollowupPromise`):** Бытовое обещание Леры отменяется при новом сообщении только в случае, если это был короткий таймер (до 15 мин) и диалог продолжился. Долгосрочные обещания на вечер/завтра не должны слетать от простой реакции пользователя «ок/договорились».

## 13. 3D-персонажи, Скелетный Ретаргетинг и Анимации в Three.js
- **«Монстры в небо» (разрыв полигонов):** Анимационные треки из FBX/Mixamo содержат `.position` (translation) для всех суставов. При ретаргетинге между моделями разного масштаба (сантиметры vs метры) чужие смещения уносят кости на десятки метров, разрывая вершины в гигантские шпили. Разрешены ТОЛЬКО вращения (`.quaternion`), а треки `.position` и `.scale` для дочерних костей фильтруются.
- **Персонажи лежат лицом в землю:** В GLTF-экспорте Mixamo корневой узел `Character` имеет компенсационный поворот +90° по X, балансирующий поворот таза `mixamorig:Hips` (-90°). Принудительный сброс `charNode.rotation.x = 0` нарушает баланс и роняет модель плашмя. Не сбрасывай нативный поворот корневого узла ассета.
- **Процедурная кинематика шага:** Вместо наложения чужих анимаций на разные скелеты, применение локальных вращений (`rotateX`, `rotateY`) относительно кэшированного rest-кватерниона (`bone.userData.restQuaternion`) обеспечивает естественную походку и синхронизацию со скоростью движения без искажения bind pose анатомии.

## 14. Контроль рода собеседника, знакомство и 3-частный ритм диалога
- **Фиксация мужского рода пользователя:** По умолчанию собеседник — парень (`users.gender = 'MALE'`). Чтобы модель не зеркалила женский род самой Леры на пользователя («ты сама», «ты пошла», «ты сказала»), в `situationStr` (`ContextBuilder.buildTemplateVariables`) и `DEFAULT_PROMPT_TEMPLATES.prompt_radiant` жестко передается: `Собеседник: {{user_name}} (парень, обращаться СТРОГО в мужском роде: ты сказал, ты пошел, ты видел, ты сам)`. Дополнительно в `processLlmOutput` (`src/ai.js`) встроен regex-санитайзер для отлова и выправления случайных женских глаголов/прилагательных в адрес собеседника.
- **Органичное знакомство и 3-частный ритм:** В `lera_rules.txt` и `lera_casual.txt` зафиксирован живой ритм диалога: `[1. Эмоция/сочувствие] -> [2. Короткое рассуждение / свой опыт] -> [3. Живой встречный вопрос]` с вариативным пропуском блоков и разбивкой на сообщения-вбросы через `|||`. Если в памяти о собеседнике мало фактов, Лера ненавязчиво вбрасывает по 1 вопросу (как зовут в реале, как нашел бота, аватарка в TG, вкусы и музыка).
- **Вызов `web_search`:** Инструмент веб-поиска явно прописан в `DEFAULT_PROMPT_TEMPLATES.prompt_tools` для фактологических вопросов, новостей, афиши и сложных тем.

## 15. Деменция контекста, ссылки в банке контента и защита от фантомной отправки (Ghost Delivery)
- **Узкое окно контекста (Sliding Window Truncation):** Если лимит событий диалога для классификатора и сборки промпта слишком мал (6-10 событий), в быстром диалоге короткими репликами лесенкой («ну скинь», «и где?», «давай жду») исходная тема разговора и обещания вымываются за 1.5–2 минуты. Всегда держи лимит не менее 20-25 событий (`getRecentConversationEvents(userId, 25)` и `priorEvents.slice(-20)`).
- **Банк контента как хранилище ссылок:** Таблица `lera_content` хранит не только медиафайлы, но и каноничные URL-ссылки (посты каналов, статьи, сайты, музыка). В `send_content` обязательны категории `'link'` и `'article'`, а в `PROMISE_PATTERNS` и Jev-критериях обязательно отслеживание слов `ссылк|стать|сайт|почитать|линк`.
- **Защита от Ghost Delivery (фантомной отправки):** Модели склонны писать текстовые маркеры доставки («держи», «вот скинула», «лови», «вот ссылка»), не вызывая инструмент и не прикрепляя реальный URL. В `response_quality.js` и `response_judge.js` включена проверка `noGhostDelivery`: если в тексте есть маркер передачи, но нет URL и не вызван тул доставки — ответ немедленно бракуется с принудительным ретраем.
- **Поддержка модульности и админки:** Кандидаты контента подмешиваются как в переменные шаблонизатора (`{{bookmarks}}`), так и отдельным динамическим системным блоком, не перетирая и не удаляя сохраненные пользователем кастомные блоки промптов в админке.

## 16. Большой контекст диалога, подбор ссылок через Jev и редактор инструментов в админке
- **Токено-ориентированное окно контекста:** В Telegram сообщения часто состоят из 5-15 слов. Жесткий слайс `slice(-20)` выкидывал контекст даже при мизерном объеме токенов (~1,500 токенов). Заменено на адаптивное окно до 50-60 сообщений с контролем бюджета символов (14,000 символов ~= 3,500-4,000 токенов диалога), что гарантирует сохранение всей нити даже при многочасовой активной переписке лесенкой.
- **Семантический отбор контента через Jev TypeSafe:** Вместо простого `LIKE`/regex поиска ключевых слов, `send_content.js` использует `selectContentWithJev` из `src/services/typesafe_client.js`. При наличии провайдера TypeSafe, Jev оценивает смысл диалога и доступных закладок из `lera_content`, выбирая наиболее органичный материал или возвращая `NONE`.
- **Редактор инструментов и бейджи шаблонов в админке:** В `admin-linear` (AiSettingsTab) добавлена отдельная вкладка «Инструменты» (Tools) с живыми тумблерами активности для каждого зарегистрированного навыка (Radiant / Native Calling), а в модалке редактирования промптов выведен интерактивный тулбар с кликабельными бейджами переменных шаблонизатора (`{{bookmarks}}`, `{{user_name}}`, `{{day_events}}`, `{{relationship}}` и т.д.).

## 17. Временные паузы в диалоге и завершение кратковременных действий (Temporal Grounding)
- **Слепая зона 3-часового порога пауз:** Ранее маркер паузы вставлялся только при перерыве от 3 часов (`gapSec >= 10800`). Если пользователь писал через 1–2 часа, реплики склеивались вплотную, из-за чего модель считала, что физические действия происходят «прямо сейчас» (например, «ешь свой бутер», хотя он был съеден час назад). Порог снижен до 20 минут (`gapSec >= 1200`), добавлен человекочитаемый маркер (`formatHumanGap`: `1 ч. 50 мин.`) и отдельная проверка паузы перед текущим ходом пользователя.

## 18. Генерация фото: развязка Identity (Лицо) и Outfit (Одежда)
- **Конфликт хардкода одежды с симуляцией Radiant:** Если базовый стиль (`style_prompt`) содержит детальное описание одежды (`Clothing Textures` и директиву `Transfer textures from ref`), диффузионная модель ставит референс выше динамической сцены и игнорирует текущий аутфит персонажа. Базовый стиль обязан содержать СТРОГО черты лица и анатомию (скулы, глаза, веснушки, стрелки, родинка), а одежда должна передаваться исключительно динамически через блок `[CURRENT SCENE & OUTFIT / DYNAMIC OVERRIDE]`.
- **Многослойность и человеческие названия одежды:** Вместо передачи сырых технических идентификаторов из базы (`trench_coat, oversize_tshirt`) функция `describeOutfit()` формирует естественные русские слои с учётом приоритета надевания (например: *«Питерский тренч поверх Футболка Богдана»*).
- **Таймауты в Telegram:** Для генерации фото в реальном времени при общении в чатах Telegram таймаут сокращен со 120с до 35с, предотвращая долгое зависание бота.
